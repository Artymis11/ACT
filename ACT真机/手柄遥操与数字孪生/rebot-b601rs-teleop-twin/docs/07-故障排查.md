# 常见问题与已知边界

## 一、打开数字孪生后，手柄不动

先确认启动的是哪个入口：

- “仅打开数字孪生”只监看，不会启动或使能控制器。
- “一键遥操与数字孪生”同时准备显示和控制窗口，但仍等待新按X才使能。
- 已有控制器时不会重复创建第二个控制器，也不会自动杀掉旧会话。

如果原控制器已经运行，查看页面或控制窗口：等待X、没有按LB、输入未回中、正在返回、反馈过期、真实电机报警，分别处理。

## 二、等待X却没有启动

检查X是否在启动前就被按住；先松开再新按。松LB、摇杆、方向键、LT/RT回中，释放其他功能键。检查XInput槽位，默认0；蓝牙配对成功不等于当前模式能提供XInput。

初始等待X时CAN尚未打开，页面可以仍显示上一会话最后记录；新会话真正产生反馈后自动切换。

## 三、X后报PCAN或设备错误

分别检查：官方驱动是否安装、DLL是否x64、DLL哈希是否对应本机注册版本、USB是否连接、当前设备是否支持PCANBasic、是否有其他控制程序占用同一设备，以及电机主电源。

当前固定使用首个USB通道，不自动枚举并改用另一套硬件。不要把Linux的`ip link set can0`命令直接当作Windows配置步骤。

## 四、X已启动，仍不动

ready后所有手动点动需要LB。X不是持续运动键。检查是否到达软件边界，尝试相反方向时应能产生允许方向意图；不要把J2/J3的0°以下视为本配置中的可用目标区。

如果控制器处于fault，不能仅凭手柄包号一直变化就判断执行链正常。

## 五、动作很慢或有轻微台阶感

默认25%档；松LB、全部回中后按RB切换。当前使用立方曲线，小幅输入速度明显低于满幅；J2半推、25%档约0.40°/s。

MIT位置编码的量化步长约0.022°，很低速度下编码目标可能呈现小台阶。平均发送接近200Hz也不能排除短时调度抖动、通信延迟、负载／摩擦或控制增益影响。

排查时分开看输入目标是否连续、高频发送参考是否连续、实际角是否跟随，避免只凭三维动画判断真实运动质量。

## 六、是否只能单轴运动

不是。左右摇杆、方向键及一个扳机可以组合；七轴意图独立计算。方向键斜向也能同时控制J5和J6。某轴到软件边界时，其他轴不会因该软边界一起锁停。

## 七、反馈过期，按X仍未恢复

X只申请符合条件的恢复：实际数据必须重新新鲜、七轴模式和运行态满足要求、无锁存真实电机故障或温度停止。

新按X失败时保留具体错误；不能通过反复重开程序把旧报警记录清空来称为修复。反馈过期之外的真实故障不由X强行清除。

故障期间若已累计120秒无操作，可能保留待处理的回零停机请求。恢复条件满足后，程序可能继续该结束流程；不能把X理解成无条件取消所有待处理停机。

## 八、为什么总把“没反应”分成多种情况

| 观察 | 不应直接得出的结论 |
| --- | --- |
| 手柄在线但机械臂不动 | 不一定是手柄断连 |
| 实测角稍超软件余量 | 不等同驱动过流 |
| 目标变化但实测不变 | 不等同机械臂已经动作 |
| 状态文件持续更新 | 不等同每个电机产生新鲜反馈 |
| 故障数字2 | 脱离通信类型不能统一解释 |
| 返回曲线结束 | 不等同精确实测到位已验收 |

## 九、报警码从哪里看

查看本次会话`status.json`和最终报告中的`fault_sources`、`last_error`、原始报文来源。type2/24六位状态中的数值2是过流位；type21完整故障字中的数值2表示驱动故障位。这是不同命名空间。

保留第一次出现时间、原始CAN ID和data，才能区分驱动报告、本地解析、通信新鲜度和软件状态。历史锁存记录不证明报警当前仍持续，也不证明已自行消除。

## 十、电源关了重开以后不动

运行中断电可能让旧软件会话保留故障和控制权记录。重新上电不会自动复位这套软件生命周期。

正常操作应先通过A或B完成结束，再关闭电源。已经处于异常会话时，外部断电接管需要实际确认当前48V已关闭、支撑独立承重，并使用当前SID；“之前关过但已重开”不能当作当前断电事实。

这类接管记录与正常回零失能分开，不能把一次重建会话当作硬件问题已验收解决。

## 十一、网页不更新或模型与实物不一致

- 看顶栏是否标明实时、过期、故障或最后姿态。
- 检查控制器与页面是否来自同一个解压目录；页面只读本仓库的运行目录。
- 只开页面且尚未启动会话时，参考零姿态不是实物测量。
- 不同目录的旧显示服务不会被公开版误当作同一实例复用；以新启动窗口地址为准。
- 模型J1～J6默认按原生角与URDF轴显示；装配零位不一致时可以只调整显示映射，不能通过改动电机零位“校正网页”。
- 夹爪显示是模型位移换算，不是实测开口宽度。

## 十二、当前已知未完全解决的部分

1. 故障／断电记录中曾出现不合理的温度回读值。页面会标为异常值，不宣称实测过热；底层状态温度解析与硬件回读仍需进一步核对，当前源码保留已有控制策略，不称此问题已修复。
2. Windows/Python调度不是硬实时；接近200Hz的平均值不能替代最长发送间隔分析。
3. Web已读取真实姿态并完成界面检查，但本轮未做新的实物同步运动及装配零位对齐验收。
4. 没有对所有手柄固件、蓝牙模式、USB-CAN设备、负载和姿态完成兼容性验证。

## 提交问题时提供什么

机械臂型号、手柄模式、Windows/Python版本、USB-CAN接口与驱动、复现步骤、阶段和错误原文即可。优先上传脱敏的最小片段，删去本机用户名、个人路径、密钥和无关训练数据。不要上传正在使用的控制命令文件。
